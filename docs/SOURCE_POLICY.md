# SOURCE_POLICY.md — 출처 레벨 정책

## 출처 레벨

| 레벨 | 의미 |
|---|---|
| **H1** | 해피니언 공식 |
| **H2** | 사부님 심연/시면에서 전달된 기준 |
| **G1** | 강서 합의 |
| **M1** | 마곡점 공식 운영 기준 |
| **K1** | 강윤의 현재 관점 또는 제안 |
| **CASE** | 실제 과거 사례 |
| **IDEA** | 아직 검토 중인 아이디어 |

`source_level`은 "누가 말했는가"만 나타낸다. "그 말의 성격이 무엇인가"
(철학/원칙/규칙/판단/절차/지표/사례/의견/질문)는 별도 축인 `content_type`이
담당한다 — 둘을 섞지 않는다. 상세: `docs/DATA_MODEL.md`, `CLAUDE.md` 6장.

## 절대 규칙

1. 서로 다른 레벨의 내용을 합쳐 하나의 "공식 기준"처럼 만들지 않는다.
2. **K1이나 IDEA를 H1/M1처럼 표현하지 않는다.**
3. CASE는 규칙이 아니다 — "과거 사례"라는 라벨을 항상 함께 노출한다.
4. 출처가 확인되지 않은 숫자/기준(가격, 할인율, 성장 단계 구간 등)은
   `review_needed`로 두고 공개 게시하지 않는다.
5. `source_level`이 H1/H2/M1이라도 `content_type`이 `philosophy`나
   `principle`이면 규칙처럼 단정적으로 표현하지 않는다 (`CLAUDE.md` 7장
   RULE vs PRINCIPLE vs JUDGMENT). "공식이니까 규칙"이 아니라
   "content_type이 rule이어야 규칙"이다.

## 화면 표시 규칙

- 모든 콘텐츠 상세 화면에는 출처 배지를 **본문보다 먼저** 눈에 띄게 표시한다.
- 배지 색상은 레벨별로 시각적으로 뚜렷하게 구분한다 (예: 공식 기준 계열 색 vs
  개인 의견/아이디어 계열 색 vs 사례 계열 색을 서로 섞이지 않게).
- `status: deprecated`인 항목은 "과거 기준" 표시를 붙이고 기본 검색 결과
  상단에 노출하지 않는다.
- `status: review_needed` 항목은 관리자 화면에서 별도로 모아 볼 수 있어야 한다.

## 충돌(conflict) 처리

같은 주제에 대해 서로 다른 출처/내용이 동시에 존재하면:

1. 임의로 하나를 정답으로 선택하지 않는다.
2. 둘 다 유지하되 `conflict` 표시를 하고 관리자 검토 큐에 올린다.
3. 관리자가 확정하기 전까지 사용자에게는 두 관점이 있다는 사실 자체를
   숨기지 않는다 (다만 어느 쪽이 맞는지는 단정하지 않는다).

## AI가 사용할 때 (Phase 4 대비)

Phase 4에서 AI가 답변을 만들 때도 이 정책을 그대로 따른다:

- 답변에는 항상 사용한 콘텐츠의 출처 레벨과 content_type을 함께 표시한다.
- K1/IDEA 기반 내용은 반드시 "이건 강윤의 개인 의견/제안입니다"처럼
  명시한다.
- H1/M1 기반 내용과 K1/IDEA 기반 내용을 한 문장에 섞어 마치 하나의
  공식 기준처럼 말하지 않는다.
- `content_type: rule`이 아닌 내용을 규칙 어투("합니다/안 됩니다")로
  답하지 않는다. 규칙/원칙/판단 세 갈래(`CLAUDE.md` 7장) 형식을 유지한다.
